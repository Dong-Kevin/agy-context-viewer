## T1 · P2：未知配额显示为 100%，单独返回的周额度被隐藏

**位置**：[app.js](../sidecars/dashboard/app.js)，第 1674、1687–1689、1718 行；当前会话入口第 798–821 行。[pricing.mjs](../sidecars/dashboard/pricing.mjs) 第 303–316、382–398 行允许返回 `null` 和独立的 weekly 窗口。

**触发与证据**：隔离探针调用真实 `groupModelQuotas`，再用 `node:vm` 执行真实前端中 `Live Model Quota Pools` 到下一卡片之间的渲染代码，注入最小 DOM 替身。

1. 输入模型 `Gemini 3.8 Flash`，`quotaInfo` 只有 `resetTime`，没有 `remainingFraction`。后端正确返回 `remainingPercent: null`，前端却生成 **`100.0%`** 和满额色条。
2. 输入同一模型、显式池 `flash`，summary 为 `{ groupId: 'flash', buckets: [{ window: 'weekly', remainingFraction: 0.2 }] }`。后端保留 **weekly 20%**、fiveHour 为空，前端仍只生成 **`100.0%`**，周额度没有显示。当前会话入口也因顶层 `remainingPercent` 为空而整体隐藏。

**根因与影响**：`pool.remainingPercent ?? 100` 把“没有数据”解释为“满额”；双窗口分支要求 `fiveHour && weekly` 同时存在，导致已知 weekly 在另一窗口缺失时丢失。用户据此判断还能使用多少额度会得到错误结论。

**建议**：分别渲染 5h / weekly 已知窗口。缺失百分比显示“未知 / 暂不可用”，有重置时间则单独保留；无数据时不画满额条。当前会话、菜单栏、悬停说明与费用页使用一致的已知值规则。不要把 weekly 值冒充 5h。

**验收**：覆盖两窗口齐全、仅 5h、仅 weekly、仅 resetTime、全缺失及真实 `0%`；未知不能变成 `0%` 或 `100%`，已知的另一个窗口不能消失。既有共享池身份断言继续通过。

## T2 · P2：语言服务失败后无限保留旧配额，却没有过期标记

**位置**：[collector.mjs](../sidecars/dashboard/collector.mjs)，第 400–409、434–436 行；会话与历史对外载荷第 1775–1784、2142–2153 行。

**触发与证据**：探针在隔离数据目录启动回环 mock Language Server，设置合成 LS 地址与测试凭据。第一次 `GetUserStatus` 成功返回 Flash 余量 80%，随后所有 LS 请求改为 HTTP 503；两次均通过 `collectTokenHistory({ force: true })` 走实际采集链路。

```text
成功：remainingPercent = 80
失败后：ok = true，remainingPercent = 80
失败前后 ETag 相同
结果没有 stale / lastSuccessfulFetchAt / quotaStatus 等状态信息
```

**根因与影响**：失败分支直接返回 `cachedHostStatus`，没有标记失败、过期时间或最大保留期限。30 秒只是成功缓存的刷新间隔，不是失败后的有效期；服务持续失败时旧值可以一直保留。历史 `updatedAt` 和会话 `scannedAt` 表示本次扫描时间，也不能证明配额已刷新。强制刷新仍得到旧值，页面无法识别断连，容易将过期余额当作当前余额。

**建议**：保留最后一次成功数据作为参考，但附带配额来源状态、成功采集时间及失败状态；状态变化纳入内容签名和 ETag，界面显示“上次更新 / 数据已过期”。恢复成功后再清除过期提示。把配额连接状态与可继续工作的本地历史采集分开，不必让整个看板失败；对 `GetUserStatus` 与 summary 单独失败也应区分。

**验收**：成功 → 单接口失败 / 全部失败 → 持续失败 → 恢复；失败时保留原成功时间并改变状态 ETag，恢复后更新。只有在无状态和业务变化时保持 ETag 稳定，避免每次轮询因当前时间而强制重绘。

## T3 · P2：没有模型容量证据时，仍以 256K 计算精确百分比并判断健康

**位置**：[collector.mjs](../sidecars/dashboard/collector.mjs)，第 1460、1541、1669 行；[app.js](../sidecars/dashboard/app.js)，第 472–478、565–580、619–620、650–664 行。

**触发与证据**：无 LS 的隔离目录中放一条本实现支持的日志事件：

```json
{
  "type": "MODEL_RESPONSE",
  "step_index": 1,
  "created_at": "2026-11-12T08:00:00Z",
  "model": "Unknown Review Model",
  "usage": { "inputTokens": 100000, "outputTokens": 1000 },
  "content": "Synthetic answer"
}
```

调用真实 `scanConversation(id, { force: true })`，结果为 `used: 101000`、`budget: 256000`、`remaining: 155000`、`percent: 39.5`。样本并没有提供模型容量。按前端已读取的分支，在默认自动预算模式下会显示“自动压缩阈值”和“运行健康”；健康结论的基础实际是代码默认值。

**根因与影响**：服务端元数据缺失和纯日志分支都补入 256000，前端 `computeEffectiveWindow` 又补一次。已有用户自定义预算入口，但自动模式也没有区分来源。未知模型、离线历史或缺字段时，无法据此证明真实剩余容量，可能产生错误的安全余量或超限提示。

**建议**：服务端容量未知时保留 `budget: null`，继续展示实际 Token 数；自动模式的百分比、剩余额度和健康判断保持未知。用户显式选择比较基准后可以计算，但始终标为用户基准。需要同时修正后端和前端默认值，否则只改后端仍会被前端补回 256K。容量来源可以用简单字段表达，无须引入新框架。

**验收**：有服务端预算时保留真实值；无预算 / 未知模型时不产生精确健康百分比；显式用户基准仍可用且清楚标注；已完成轮次但预算未知时不能误写成“待首轮请求”。

## 优化顺序建议

以下为建议，未实施，也不因列入本文就成为已确认范围。

1. **先修 T1–T3，并补行为用例。** 统一“已知、未知、估算、过期”的最小数据契约，修复采集、JSON 与展示之间的信息丢失。可在现有测试中加入上述边界，不需要新增测试框架。
2. **给费率表增加可追溯证据。** `pricing.mjs:6–108` 有统一核验日期和按日期 / Token 档位的规则，但缺少逐模型来源 URL。建议为模型费率记录来源、核验日期、适用区间，保持离线可用，并覆盖日期切换与长上下文临界点。本轮没有逐一核验所有官方费率，不能宣称表中的价格正确或错误。参考 ccusage 的固定快照思路，不默认引入联网抓价、第三方运行时依赖或自动 CI。
3. **补平台能力与验证矩阵。** 当前缺口是 Windows PowerShell 5.1 / 7 + cmd、Linux 桌面浏览器回退、Node.js 18 最低版本的实测。优先覆盖中文 / 空格路径、命令入口、安装升级、关闭生命周期。测试替身通过与真实平台通过应分开记录；README 已说明浏览器回退差异，可在此基础上补验收结果。
4. **先测大日志，再决定增量采集。** `collector.mjs:1920–1923` 对变化文件仍整文件读取 / 切分；部分 Map 没有容量或过期策略。先用合成 10 / 100 MB 日志测刷新延迟、RSS、扫描时间；若证实有瓶颈，再做有界缓存和按偏移读取，并覆盖半行写入、截断、轮转及模型切换状态。本轮没有性能基准，不声称这已造成卡顿或重写能提升多少。
5. **历史导出与配额趋势后置。** 可借鉴 ccusage 的 `since / until / source` 筛选，复用已有 JSON 入口；参考 CodexBar 做配额快照时要带来源时间、账号与池身份，不能跨重置窗口连接出虚假趋势。现有热力图已经覆盖不少统计需求，不建议为了功能数量立即扩展。

**Rust 判断不变**：本轮发现的是状态语义和展示问题，换语言不会自动修复。当前零依赖 Node.js 核心可以继续跨平台使用；除非实测证明性能瓶颈，或已经确定需要独立原生桌面产品，否则不建议整体重写。平台原生能力与业务采集分开演进即可。
